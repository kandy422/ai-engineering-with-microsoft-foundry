# Lesson 8.5 · Managed fine-tuning in Foundry

Train on fictional support tickets and measure whether adaptation changes exact routing accuracy on unseen tickets. This small balanced dataset demonstrates the workflow. Even a perfect score on 12 cases cannot establish production performance.

1. Install Python 3.12. From this directory run `py -3.12 -m pip install tiktoken`, then `py -3.12 lifecycle.py validate`. Expect 24 training, 6 validation and 12 held-out rows. Review the hashes and one message exchange per file. The tokenizer can fetch its encoding data on first use.
2. Use your authorized East US 2 Foundry project and sign in with Microsoft Entra. Training requires Foundry User. Deployment requires Foundry Owner or approved equivalent deployment permissions. The evaluation identity needs inference access to both deployments. Verify available quota and permissions first. [Microsoft SFT guide](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/fine-tuning)
3. In Foundry open **Build → Fine-tune → Fine-tune**. Select **gpt-4.1-mini (2025-04-14)**, **Supervised fine-tuning**, **Global** training, and **3 epochs**. Leave batch size and learning-rate multiplier automatic. Upload only training.jsonl and validation.jsonl to their respective slots. Capture the review screen and submit one approved job.
4. Monitor the exact job ID. Save the terminal job response as job.json using `GET /openai/v1/fine_tuning/jobs/{job-id}` on the approved resource, and export the events and metrics. Keep its actual status, trained tokens, model ID and result file IDs. Retain a failure receipt if the job fails. Cancel through the exact job detail page if needed.
5. Deploy the resulting model as **Developer** and the exact base snapshot as **Global Standard**, in the same account. Use the smallest capacity accepted for each SKU. Export each record with `az cognitiveservices account deployment show --resource-group <group> --name <account> --deployment-name <name> --output json` to UTF-8 files base.json and adapted.json. Check both provisioning states, model IDs and base version.
6. In the same signed-in CLI session, run the command below during the planned 30-minute capture window. It sends 24 requests with identical prompts and inference settings, alternates request order, and saves each receipt. Review both scores and both directions of change. Report a tie or regression as observed. If the run stops, reconcile the requests and retained receipts before deciding how to proceed.

```powershell
py -3.12 lifecycle.py evaluate --endpoint https://<account>.openai.azure.com --base-receipt base.json --adapted-receipt adapted.json --job-receipt job.json --output paired-run --approved-live-run
```

7. Export all receipts and the score summary before teardown. Remove only the dedicated deployments after verifying their exact resource IDs. Run `az cognitiveservices account deployment delete --resource-group <group> --name <account> --deployment-name <name>` once for each dedicated deployment, then verify absence. If the base deployment was explicitly reused, leave it in place. The Developer deployment has a 24-hour lifetime, no hourly hosting charge and no availability SLA. Clean up the exercise files and custom model after preserving the evidence and removing the deployment. [Deployment lifecycle](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/fine-tuning-deploy)

The instructor uses the Files API and Fine-tuning API for submission, Azure CLI for deployment, and the same paired evaluator used by learners. The instructor scripts bind to the course's approved account. Follow the portal and deployment steps above for your own account. At one request per minute per deployment, the evaluator spaces calls to the same endpoint by 65 seconds. Allow about 14 minutes for the pair run. Use fictional data in this Global workflow.
