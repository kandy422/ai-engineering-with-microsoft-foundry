# Module 14 capstone security acceptance

From this directory, run `py -3.12 check.py <sanitized-receipt.json>` against the coordinator’s evidence. The checker reads JSON and makes no network requests. Exit zero means the receipt meets the assertions. The receipt must point to actual app, retrieval and storage evidence. Keep the covered revision and image digest with the recording.

## Fixture and evidence contract

- Seed synthetic users A and B with distinct customer scopes in the same Entra tenant. Seed each order into its own scope, and confirm ORD-9999 is absent. Seed a ticket for A and one coordinator-approved synthetic action. Record the exact ticket and action as `ticketA` and `actionA` in the run manifest.
- Seed two active delivery documents with the same question, different answers and distinct citations. Each must be visible only to its owner. Capture the IDs actually supplied to the model as well as the returned citation. A correct answer alone does not verify the retrieval boundary. Arrange the fixture so each owner has exactly one applicable active result.
- Use the hosted route bodies from Module 16: `{"id":"ORD-1042"}`, `{"text":"What is my standard delivery window?"}`, `{"ticket":"<ticketA>","action":"<actionA>"}`, and `{"proposal":"<returned ID>"}`. Assign customer scope from verified claims. Test unexpected identity fields in a local serializer contract test and test untrusted evidence with a preclassified local fixture at the application boundary. Those two checks establish local behavior. Hosted detector behavior remains a separate evidence gap.
- Use the same proposal for the actor check, the authorized approval, the repeat and the post-restart repeat. Before restarting, capture the committed side effect and idempotency record. After restart, verify a different process or replica instance is serving the same app revision against the same store. Use authenticated store or audit evidence to count committed effects. Response `writes` alone is insufficient.
- Receipt top-level fields: `mode` (hosted), `runId`, `revision`, `indexVersion`, `storeAlias`, `seedCitationA`, `seedCitationB`, `instanceBefore`, `instanceAfter`, `restartEvidenceRef`, `durableWriteCount`, `durableEvidenceRef`, and `cases`. Each case records `id`, `mode`, `http`, `status` when supplied, observed `writes`, and `evidenceRef`. Record `sensitiveDataReturned` for denial cases, `citation` and `contextCitationIds` for search cases, and `proposalRef` for the approval chain. The untrusted fixture also records `sourceWasPreclassified` and `toolDispatchCount`.
- Verify the domain status names in cases.json against the final Module 16 adapter. Keep explicit status assertions and record any agreed vocabulary change before acceptance. HTTP 503, a fixture health mode, a store counter inferred from output, or a restart without a distinct process receipt leaves acceptance pending.

Verify the Search schema supports filterable tenant, customer and active-state fields. Record the deployed index/version and preserve the query prefilter and the application’s scope check on returned rows.

## Learner packaging, cost and cleanup

Retain resources still needed for downstream verification.


## Delegated users and certificate clients

Use an actual Entra v2 delegated API token with Support.Access for the human case. The two course-owned service principals use certificates and the dedicated Support.Automation application role. Record their exact allowlisted client IDs and configured subject-to-customer mappings in the restricted coordinator manifest. Use aliases in the learner and review receipts.

For each identity case, attach sanitized identityEvidence with kind, tokenSource (entra-live), signatureIssuerAudienceValidated, and validationRef. The validation reference must identify which layer validated the signed token for the target tenant and API audience. For success, also record clientAlias, subjectAlias, clientAllowlisted, subjectMapped, resolvedCustomerScope and delegatedScopePresent or dedicatedRolePresent. For service principals, record credentialMethod (certificate) and credentialEvidenceRef from sanitized token-acquisition evidence. A JWT role alone does not establish certificate use.

For each service denial, isolate one authorization condition. The other two checks should match the allowed configuration. Record dedicatedRolePresent, subjectMapped, clientAllowlisted and authorizationOutcome. The expected result is 403 after signature, issuer and audience validation, with no resolved scope, disclosure or writes. Token issuance rejection is separate evidence. If Entra prevents issuance of a valid role-less token, keep the valid-token application denial pending. An ingress denial alone does not prove the application reached its authorization checks.

The coordinator owns allocation, certificate handling and any temporary fixture configuration. Keep usable tokens, private keys and raw JWTs out of receipts, logs and learner downloads.
